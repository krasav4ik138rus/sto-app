# STO Decisions

Этот документ фиксирует продуктовые и технические решения для первого STO MVP. Он нужен, чтобы не смешивать старую идею Python/Telegram-бота с текущим Android-first приложением на Expo, backend API и PostgreSQL.

## Product Scope

- Приложение внутреннее: им пользуются сотрудники СТО, мастера, директора и администраторы.
- Клиентских аккаунтов в MVP нет.
- Публичной регистрации в MVP нет: сотрудников создает или подключает администратор/директор.
- Основной сценарий MVP: заказ-наряд, автомобиль, клиент, акт осмотра, диагностика, рекомендации, статусы, фото и файлы.
- Отчетность директора строится на нормализованных сущностях заказов, статусов, рекомендаций и вложений.

## Auth And Accounts

- Используем существующую модель `User` из шаблона.
- Не создаем отдельную таблицу `users`.
- Рабочие данные сотрудника храним в `StaffProfile`, который расширяет `User`.
- В MVP используем email/password auth.
- Social auth поля шаблона (`appleSubject`, `googleSubject`) не удаляем, но не используем в MVP.
- IAP/payments модели шаблона не удаляем, но не используем в MVP.
- Push-модели шаблона не удаляем: они пригодятся позже для уведомлений.

## Roles

Роли MVP:

- `MECHANIC`: выполняет осмотры, диагностику, добавляет фото и рекомендации.
- `MASTER`: ведет заказ-наряд, меняет статусы, согласует рекомендации.
- `DIRECTOR`: смотрит отчетность, контролирует загрузку и статусы.
- `ADMIN`: управляет сотрудниками, филиалами и системными настройками.

## Naming

- В коде и API используем название `Vehicle`, а не `Car`.
- В UI можно показывать русское "автомобиль".
- Старые bot-поля `car_brand_model`, `car_vin`, `car_plate`, `car_mileage` переносятся в домен `Vehicle` и `WorkOrder`.

## Organization Model

- В seed/dev-данных на старте достаточно одной организации и одного сервисного центра.
- Схема сразу поддерживает несколько организаций и филиалов, чтобы не переделывать основу для сети СТО.
- `Organization.slug` делаем обязательным и уникальным: это удобно для админки, seed-данных и будущей маршрутизации.
- `Organization.timezone` по умолчанию `Europe/Moscow`.

## Attachments

- В MVP храним metadata вложений: тип, ключ хранилища, URL, имя файла, MIME type, размер, подпись, видимость.
- Реальную загрузку файлов, presigned upload, thumbnails и offline upload queue делаем отдельными этапами.
- Вложения можно привязывать к заказ-наряду, акту осмотра, диагностике или рекомендации.

## Forms

- Акт осмотра и диагностика хранят ответы в JSON (`dataJson`), потому что состав полей будет меняться.
- Стабильные бизнес-сущности остаются нормализованными: заказ, клиент, автомобиль, рекомендации, статусы, вложения и аудит.
- `FormTemplate` не добавляем в Prisma на этом этапе. Он остается future/optional, пока конфигурации форм живут в shared code/contracts.

## Out Of MVP

- Клиентский портал и клиентские аккаунты.
- Публичная регистрация.
- Social auth как рабочий сценарий.
- IAP/payments.
- Webapp/website.
- PDF export.
- Chat.
- Production deployment.
- Реальное объектное хранилище для файлов.
