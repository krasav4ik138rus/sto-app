# Mobile UI для СТО

Android-приложение должно быть рабочим инструментом, а не лендингом. После авторизации основной экран - список заказ-нарядов. Текущий mobile baseline содержит auth/paywall/component catalog; STO-навигация будет следующим этапом.

## Список заказ-нарядов

Формат: карточки + поиск + фильтры.

Карточка показывает:

- номер заказ-наряда;
- статус;
- автомобиль;
- гос. номер и VIN;
- пробег;
- клиента;
- ответственного;
- время последнего изменения;
- индикаторы: акт, диагностика, фото, рекомендации.

Поиск/фильтры:

- номер заказа;
- гос. номер;
- VIN;
- клиент;
- статус;
- филиал для директора/admin.

## Создание заказ-наряда

Поля:

- номер заказа;
- клиент или создание клиента;
- автомобиль или создание автомобиля;
- пробег;
- причина обращения;
- филиал/ответственный, если роль позволяет.

После создания пользователь попадает в карточку заказ-наряда.

## Карточка заказ-наряда

Центральный экран работы.

Блоки:

- заголовок: номер, статус, авто, гос. номер, VIN, пробег, клиент;
- быстрые действия: акт, диагностика, рекомендации, фото/файлы, сводка;
- последняя активность;
- краткие рекомендации;
- краткие вложения;
- totals.

Статусы меняются с учетом роли и пишутся в `WorkOrderStatusHistory`.

## Акт осмотра

Android-адаптация:

- секции как tabs/segmented control/вертикальный список;
- поля текущей секции идут карточками;
- progress заполнения;
- save, save and exit, next section;
- позже autosave/draft.

Секции:

- общие данные;
- секретки и запасные части;
- передняя светотехника;
- задняя светотехника;
- щетки и омыватели;
- подкапотное пространство;
- итоговые рекомендации.

Контролы:

- `text`: input;
- `text_multiline`: multiline input;
- `number`: numeric keyboard;
- `choice`: segmented/radio;
- `condition3`: три состояния `ok`, `attention`, `urgent`.

## Диагностика

Android-адаптация:

- сначала список категорий;
- внутри категории карточки позиций;
- `side: both` показывает левую и правую сторону;
- `side: none` показывает одну строку;
- цены появляются только при `not_ok` или `recommend_service`.

Категории:

- ходовая спереди;
- ходовая сзади;
- тормозная система;
- стояночный тормоз;
- трансмиссия;
- итоги и развал-схождение.

Важно для UX:

- крупные touch targets;
- быстрый выбор статуса;
- sticky save footer;
- сворачивание заполненных секций;
- предупреждение о несохраненных изменениях.

## Рекомендации

Список:

- текст;
- статус;
- цена запчастей;
- цена работ;
- итог;
- связь с диагностикой/актом;
- автор и дата.

Действия:

- добавить;
- редактировать;
- изменить цены;
- перевести `suggested -> approved -> done`;
- позже `declined`;
- привязать к пункту диагностики.

## Фото и файлы

Возможности:

- сделать фото с камеры;
- выбрать фото/файл;
- добавить подпись;
- загрузить через backend-issued presigned URL;
- привязать к заказу, акту, диагностике или рекомендации;
- смотреть photo grid;
- удалить/soft-delete по правам.

MVP: фото + простые метаданные. Видео, thumbnails и offline queue позже.

## Итоговая сводка

Показывает:

- заказ и статус;
- клиент/авто;
- только проблемные/важные пункты акта;
- диагностику `not_ok` и `recommend_service`;
- рекомендации с ценами;
- сумму запчастей;
- сумму работ;
- общую сумму;
- количество фото/файлов.

Действия:

- перейти к редактированию источника;
- позже PDF/export/share;
- закрыть/согласовать заказ по роли.

## Пользователи и роли

Для admin/director:

- список сотрудников;
- роль;
- филиал;
- активен/деактивирован;
- изменение роли;
- позже история действий.

В MVP лучше сначала сделать backend role guards, а UI управления пользователями - после основного рабочего процесса.

## Отчетность для директора

Android-минимум:

- заказы по статусам;
- заказы по филиалам;
- выполненные/закрытые заказы;
- рекомендации suggested/approved/done;
- totals по запчастям/работам;
- активность сотрудников;
- покрытие заказов фото/актами/диагностикой.

Детальные dashboard лучше вынести в будущий webapp.
